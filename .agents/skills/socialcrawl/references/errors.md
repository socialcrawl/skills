# Errors

Read this when a call fails. The full code table (status, retryable, what to do) is generated in [api-overview.md](api-overview.md#error-codes); the `error.details` reasons are in [api-overview.md](api-overview.md#error-details-errordetails).

**Fastest fix:** paste the failed status and body into the free `GET /v1/utility/explain-error?status=<code>&body=<error JSON>` (add `request=<the path and query you sent>` to get a corrected request back). It returns the fault in plain words, the steps that fix it, and whether retrying the same request can succeed. Nothing is fetched and it costs 0 credits.

## Classify before retrying

Branch on `error.retryable` first, then on `error.details`, never on the status alone.

- **Fix before retrying (`retryable: false`):** `MISSING_API_KEY`, `INVALID_API_KEY`, `INSUFFICIENT_CREDITS`, `KEY_BUDGET_EXCEEDED`, `INVALID_REQUEST`, `METHOD_NOT_ALLOWED` (the `Allow` header names the right verb), `ENDPOINT_NOT_FOUND`, `PAYLOAD_TOO_LARGE`, `IDEMPOTENCY_KEY_CONFLICT`, `IDEMPOTENCY_KEY_PAYLOAD_MISMATCH` (use a fresh key for the changed payload), `IDEMPOTENCY_REPLAY_UNAVAILABLE`, and every `COHORT_*` code. Explain the corrective action and do not repeat the same request.
- **Wait, then retry the same request:** `RATE_LIMITED`, `CONCURRENCY_LIMIT` (`Retry-After: 1`), `SERVICE_UNAVAILABLE`, and `409 IDEMPOTENCY_IN_PROGRESS` (`Retry-After` 1-30 s; resend with the **same** `Idempotency-Key`). Honour `Retry-After`, then back off exponentially with jitter. A `Retry-After` longer than a minute (for example `3600` for a source that is down in one market) means stop and report, not wait in a loop.
- **Transient upstream failure:** `UPSTREAM_ERROR` (502, or 504 on a timeout) and `INTERNAL_ERROR`, refunded. If `error.details.retry_with` is present, `retryable` is `false` and there is no `Retry-After`: the same request fails the same way, so resend once with exactly the params it names (for example `proxy=auto` on `web/scrape`). If `error.incident` is present, stop calling that platform and poll `GET /v1/status/{platform}` every few minutes. Otherwise retry at most once, then report the outage with the endpoint and `request_id`, never the credential.
- **Not found:** `RESOURCE_NOT_FOUND` is a valid empty outcome, not a retry loop.
- **Discover runs and the events feed:** `RUN_NOT_FOUND` / `SCHEDULE_NOT_FOUND` (wrong id, or another account's): list your runs or schedules, or start again. `RUN_STATE_CONFLICT` (409): read the run and do what `data.run.next_step` says (a completed run takes `more`, not `resume`). `RUN_EXPIRED` (410): retention passed, start a new run. `NEEDS_ASYNC` (422): drop `async=false` and follow the 202's `data.next.status_url`. `CURSOR_EXPIRED` (410): restart the feed from `details.oldest_cursor` (or `cursor=oldest`) and tell the user the events in `missed_from`..`missed_until` are gone (30-day retention).

## Act on `error.details`

Every error carries `error.retryable`, and many carry `error.details.reason`; act on it rather than on the status alone:

- **402** (`balance_too_low`, `key_budget_reached`) always says `retry_will_succeed: false`: **never retry a 402 unchanged**. The same request fails until the balance or that key's limit changes. Point the user at `top_up_url` or `key_settings_url`; `key_name`, `key_prefix` and `account_email_masked`, when present, say which key and account ran out. A key budget is a lifetime cap on that key's net spend (refunds give it back; it never resets on its own), so on `key_budget_reached` the `credits_remaining` is the healthy account balance: the user raises the limit or resets the key's usage in Dashboard → API Keys, or uses another key. On a metered call `pricing: "ceiling"` means the quoted credits are the maximum hold (unused credits are refunded) and `credits_typical` is what a call like it is usually charged; `pricing: "exact"` means it is charged what it holds. `lower_cost_options` lists each param that lowers the hold, with the `value` to send (`null`: leave it out) and the `credits_required` it gives, and `credits_required_cheapest` is the hold with all of them. When one of those fits `credits_remaining`, offer the user that smaller request, or a top-up for the full one.
- **400 `page_limit`** (`max_page`, `narrow_with`): the source has no further pages for this query; stop paging and narrow the query instead. It is the end of the walk, not a failure.
- **400 with `did_you_mean`**: a parameter or value was misnamed. `error.details.received_unknown` lists the names the endpoint did not recognise, `missing` the required one it did not get, and `did_you_mean` the name it takes (`You sent term; this endpoint takes query`). Resend under that name; it is free.
- **400 `INVALID_REQUEST` naming a param on a single-source lane** (for example `weibo/profile`, `goodreads/quotes`, `airbnb/search`, `airbnb/listing/availability`): the value you sent is wrong for that source (an id or URL it cannot read, a date it refuses). It is free and final; fix the param named in `error.details.param` and resend. These lanes used to answer a refunded, retryable 502 for the same input, so do not retry one unchanged.
- **400 `unsupported_date_filter`**: `since` / `until` (or a copied spelling such as `published_after`) on a list whose rows carry no date. Drop the date.
- **404 `account_gone` / `account_private` / `handle_unresolved`**: follow `error.details.suggestion` once (for a YouTube handle, retry with the stored `channelId` to tell a rename from a removal), then report. `site_not_supported` on `web/scrape` is final; its `suggestion` names the SocialCrawl endpoint for a social link.
- **404 `ENDPOINT_NOT_FOUND`** may carry `details.did_you_mean` (paths), `did_you_mean_platform` and `retry_with` (the whole corrected URL, for example for a bare `/search`); check the live registry (`GET /v1/utility/endpoints?search=`, free) before saying something is unsupported. On `/v1/web/jobs|monitors|sessions/{id}` it means the id is unknown for this key.
- **5xx** carry `error.status_url` and, during an open incident, `error.incident` (`id`, `title`, `status`, `impact`, `url`).

## Not errors: `data._warnings` and `meta.hint`

A `200` can still carry advice. `data._warnings` reports a parameter that was ignored or cleaned (a `Query:` label stripped from a search term, a `fields=` path that does not exist, with the path it probably meant) and a handle that resolved to a different account. `meta.hint`, at the envelope root, names one other call that does the job in fewer steps; when that call costs more, its `message` says both prices, so follow it only within what the user authorised. It reaches a key at most once a day per pattern, never on an error; send `X-SocialCrawl-Hints: off` to stop it.

## Retrying paid calls

For a retryable paid non-streaming request, send an `Idempotency-Key` before the first attempt and reuse it only for the identical payload (same params, same `fields`). A GET with `Accept: text/event-stream` cannot carry an `Idempotency-Key` (free 400); do not automatically retry streaming requests. Never exceed one automatic retry unless the user explicitly asks for continued retries.

**Some POSTs ignore `Idempotency-Key`, so never auto-retry them:** `POST /v1/web/agent`, `/v1/web/sessions`, `/v1/web/monitors`, `/v1/web/parse`, `/v1/monitors` and `/v1/trustpilot/reviews/history`. A resend creates (and, where it bills, bills) a second run, session, monitor or job. Read the list route (`GET /v1/web/jobs`, `GET /v1/web/sessions`, `GET /v1/monitors`) to see whether the first one landed. On `POST /v1/web/crawl` and `/v1/web/batch-scrape` a repeated key returns the existing job (200, 0 credits) without comparing the body.

**A client timeout does not cancel the call.** The server finishes it, charges it and writes it to the cache. Resend the identical request (same or new key) and, within the endpoint's cache TTL, it comes back free from cache (`X-Cache: HIT`). Size your timeout from `recommended_timeout_s` in `GET /v1/utility/endpoint?id=` (60 s is safe almost everywhere).

Failed calls are refunded (upstream errors, circuit-breaker rejections, timeouts, not-found, empty results). `credits_used` on an error envelope is the committed net charge: 0 in almost every case, the kept legs on a partially failed composite. A request rejected for bad params, a page past the source's last page, or a rate limit never deducts at all.
